**文档状态：** 草稿 v0.1

## 1. 文档目的

本软件需求规格说明书（SRS）定义一个以娱乐为目的的社区评分网站的初始产品需求。文档记录已经确认的产品决策，将其与为满足课程要求而提出的建议区分开，并为功能需求、数据模型、线框图、实现、测试、部署和安全建立可追踪的共同基线。

本文件仍是早期草稿。标记为 **暂定（Provisional）** 的需求仍需团队确认；标记为 **待定（TBD）** 的事项必须在 Assignment 1 报告定稿前解决。

## 2. 产品愿景

Rate Anything 允许那些随时对他人看法感到好奇的人，为几乎任何事物创建和发现有趣的评分。评分对象既可以是冰箱之类的实体产品，也可以是熬夜之类的抽象概念。成员可以创建评分对象，定义判断它的评分维度，提交分数并发布结果。其他成员可以找到该对象、查看相关社区内容、讨论某次评分，并复用已有的评分维度提交自己的分数。

网站以娱乐为目的。结果分数（Result Score）代表社区成员表达的个人观点，并不追求客观、权威或事实上的真实性。

### 2.1 价值主张

本产品提供：

- 一种低门槛的方式，让用户能够对任何实体或抽象评分对象表达观点；
- 一种比无条件星级评分更有结构的方式，允许成员自行定义评分维度；
- 一种比较不同用户如何使用同一评分方案判断同一对象的方式；
- 一个可搜索的评分、文字感想、图片和讨论集合；
- 一种允许主观、幽默结果存在的轻松娱乐体验。

### 2.2 目标用户

主要用户是在空闲浏览时，随意想知道其他人如何看待某个事物，并希望获得轻量娱乐体验的人。

当前草稿定义三种角色：

| 角色 | 说明 | 预期权限 |
|---|---|---|
| 访客（Visitor） | 尚未登录的人 | **暂定：** 只能搜索和阅读公开内容 |
| 成员（Member） | 已注册并通过认证的社区参与者 | 创建评分对象和评分方案、提交评分、上传图片、评论以及管理自己的内容 |
| 管理员（Moderator） | 负责事后内容审核的特权成员 | 拥有全部成员权限，并可通过自定义管理面板检查和删除违规内容 |

## 3. 产品范围

### 3.1 已确认的范围

- 创建一个可评分对象（Thing），其内容可以是实体或抽象概念。
- 按名称搜索现有评分对象。
- 通过定义用户自选的评分维度（Criterion），为评分对象创建评分方案（Rating Scheme）。
- 为评分方案中的每个评分维度提交分数。
- 计算结果分数，并将其存储在关联的评分对象下。
- 允许多名成员为同一个评分对象创建相互独立的评分方案。
- 允许其他成员复用已有评分方案并提交自己的分数。
- 当用户打开评分对象时，显示所有相关评分提交、文字感想、图片和讨论。
- 在其他成员的评分提交下发表评论。
- 允许任何社区成员添加新的评分对象，无需管理员事先批准。
- 允许管理员删除违法、暴力、色情或其他被禁止的内容，尤其关注用户上传的图片。
- 在可行的情况下保留现有 Score-O-Matic 原型的视觉风格和有价值的交互设计，但不要求完全复刻其实现。

### 3.2 暂定的 MVP 边界

推荐的 MVP 是一个以单独评分对象页面为核心的社区网站。现有原型中的个人加权排名流程本身不属于 MVP 的硬性要求，但可以复用其配色、卡片、分步评分流程和结果展示方式。

为满足课程要求，暂定以下五项只能由已认证用户使用的核心能力：

1. 创建并发布评分对象。
2. 创建评分方案并发布第一条评分提交。
3. 复用已有评分方案，发布或更新自己的评分提交。
4. 在其他成员的评分提交下发表评论并参与讨论。
5. 举报可能违规的内容，交由管理员检查。

第五项能力标记为 **暂定**，因为团队尚未明确确认用户举报功能；不过该功能能够为事后内容审核提供必要的工作流。

### 3.3 MVP 明确不包含的内容

- 声称某个分数客观真实或具有专业权威性。
- 电子商务、支付、下单或商品库存功能。
- 原生移动应用。
- 私信或实时聊天。
- 完整的社交关注网络。
- AI 生成的官方评分。
- 机器学习驱动的自动推荐。
- WebSocket 功能，除非后续将其选为 Assignment 2 的 Modern Web 方案。
- 完整重建当前独立运行的 Score-O-Matic 工具。

## 4. 领域模型

### 4.1 标准领域概念

| 概念 | 定义 |
|---|---|
| 评分对象（Thing） | 被用户选作评分主题的任何实体、产品、体验、想法或抽象概念。 |
| 评分方案（Rating Scheme） | 专门为一个评分对象创建、可以被重复使用的评分结构。 |
| 评分维度（Criterion） | 评分方案中一个具有名称的打分维度；它不是用于搜索的普通标签。 |
| 评分提交（Rating Submission） | 一名成员使用一个评分方案完成的全部维度分数，可以附带文字和图片。 |
| 结果分数（Result Score） | 根据一条评分提交计算出的数值结果。 |
| 评论（Comment） | 附属于一条评分提交的讨论内容。 |
| 媒体资源（Media Asset） | 随评分提交上传的图片。 |
| 内容举报（Content Report） | 请求管理员检查可能违规内容的记录。 |

### 4.2 领域规则

1. 一个评分对象可以拥有多个评分方案。
2. 一个评分方案必须只属于一个评分对象，并且只有一个创建者。
3. 一个评分方案必须至少包含一个评分维度。
4. 一个评分维度必须只属于一个评分方案。
5. 一条评分提交必须只使用一个评分方案。
6. 一条完成的评分提交必须包含该评分方案每个有效评分维度的一条维度分数。
7. 评分方案的创建者可以使用该方案发布第一条评分提交。
8. 其他成员可以复用该评分方案，但不能改变其中的评分维度。
9. 如果成员希望使用不同维度判断同一评分对象，可以创建另一个评分方案。
10. 一条评论必须只属于一条评分提交。
11. 每个媒体资源都必须能追溯到上传它的成员以及它出现的社区内容。
12. 管理员可以删除违规内容，而不删除同一评分对象下无关的合法内容。
13. 结果分数必须被呈现为主观的社区娱乐内容，而不是经过验证的事实。

### 4.3 示例场景

1. 成员 A 搜索 `冰箱`，没有找到匹配的评分对象。
2. 成员 A 创建评分对象 `冰箱`。
3. 成员 A 创建名为 `冰箱有多伟大？` 的评分方案，并加入 `实用性`、`噪音` 和 `快乐程度` 等评分维度。
4. 成员 A 为每个维度打分，添加文字感想和图片，然后发布评分提交。
5. 成员 B 搜索 `冰箱`，看到评分对象页面、成员 A 的结果分数、评分维度、文字感想、图片和讨论。
6. 成员 B 复用成员 A 的评分方案，提交自己的维度分数，并得到一条独立的结果分数。
7. 成员 B 在成员 A 的评分提交下发表评论。
8. 如果上传的图片违反内容政策，管理员删除该图片，并在适当情况下保留合法的评分和讨论。

## 5. 功能需求

所有稳定的功能需求均使用“系统应……”的陈述方式。优先级分为“必须（Must）”“应该（Should）”和“可以（Could）”。验收证据描述验证该需求所需的最低可观察行为。

### 5.1 身份认证与访问控制

| ID | 需求 | 优先级 | 验收证据 |
|---|---|---:|---|
| FR-AUTH-01 | 系统应允许新用户使用唯一标识符和密码注册成员账号。 | 必须 | 有效注册只创建一个账号；重复标识符和无效密码被拒绝，并显示面向用户的反馈。 |
| FR-AUTH-02 | 系统应允许已注册成员安全登录并建立已认证会话。 | 必须 | 有效凭据可以建立会话；无效凭据不会泄露某个账号是否存在。 |
| FR-AUTH-03 | 系统应允许已认证成员退出登录，并使当前会话失效。 | 必须 | 退出后的会话不能访问仅限已认证用户的端点。 |
| FR-AUTH-04 | **暂定：** 系统应允许访客在不登录的情况下搜索和阅读公开的评分对象、评分提交、图片与评论。 | 应该 | 未登录访客可以打开公开只读页面，但不能执行写操作。 |
| FR-AUTH-05 | **暂定：** 用户在创建、编辑、评分、评论、上传、举报或删除社区内容前，系统应要求其完成身份认证。 | 必须 | 每个受保护的用户界面和后端端点都会拒绝未经认证的写请求。 |

### 5.2 评分对象发现与创建

| ID | 需求 | 优先级 | 验收证据 |
|---|---|---:|---|
| FR-THG-01 | 系统应允许已认证成员创建具有非空名称的评分对象，并标明它是实体还是抽象概念。 | 必须 | 有效对象被保存并可以搜索；空名称被拒绝。 |
| FR-THG-02 | 系统应允许任何已认证成员直接发布新评分对象，无需管理员事先审批。 | 必须 | 新建的有效对象立即公开可见，除非被技术验证规则自动拦截。 |
| FR-THG-03 | 系统应允许用户按名称搜索评分对象。 | 必须 | 查询返回匹配对象；没有匹配项时清楚显示空结果状态。 |
| FR-THG-04 | 系统应显示评分对象详情页，其中包含与该对象关联的所有有效评分方案和评分提交。 | 必须 | 打开评分对象时会显示所有有效贡献，并且不会暴露已被管理员移除的内容。 |
| FR-THG-05 | 系统应显示当前评分对象页面上各评分提交关联的文字感想、有效媒体资源、结果分数和评论。 | 必须 | 评分对象页面呈现完整的有效社区内容层级，并正确标明每项贡献的作者。 |
| FR-THG-06 | **暂定：** 当成员提出的评分对象名称与已有名称相似时，系统应在可能创建重复对象前发出提醒。 | 应该 | 疑似重复的名称会让用户选择使用已有对象，或继续创建一个不同对象。 |

### 5.3 评分方案创建

| ID | 需求 | 优先级 | 验收证据 |
|---|---|---:|---|
| FR-SCH-01 | 系统应允许已认证成员为已有评分对象创建评分方案。 | 必须 | 有效方案只存储在一个评分对象下，并归属于其创建者。 |
| FR-SCH-02 | 在发布评分方案前，系统应要求创建者至少添加一个非空评分维度。 | 必须 | 没有有效评分维度时，发布功能保持禁用。 |
| FR-SCH-03 | 系统应允许创建者在发布前添加、重命名、重新排序和移除评分维度。 | 必须 | 保存的评分方案与最终的有序评分维度列表一致。 |
| FR-SCH-04 | 系统应阻止复用已发布评分方案的成员更改该方案的评分维度。 | 必须 | 非所有者的评分流程只读取已发布维度，不提供任何维度修改操作。 |
| FR-SCH-05 | **暂定：** 当评分方案创建者以后编辑方案时，系统应保留已有评分提交所使用的评分维度定义。 | 应该 | 允许修改方案后，历史评分结果仍可被复现。 |

### 5.4 评分与分数计算

| ID | 需求 | 优先级 | 验收证据 |
|---|---|---:|---|
| FR-RAT-01 | 系统应允许已认证成员为所选评分方案的每个评分维度分配一个有效分数。 | 必须 | 只有全部必填维度分数都处于已配置范围内时，提交才会被接受。 |
| FR-RAT-02 | 系统应按照公开的评分规则，根据提交的维度分数计算结果分数。 | 必须 | 在评分方案版本和维度分数相同时，后端返回相同的结果分数。 |
| FR-RAT-03 | 系统应在后端计算并验证结果分数，而不能信任客户端直接提交的计算结果。 | 必须 | 修改浏览器请求中的结果字段不能改变后端存储的计算结果。 |
| FR-RAT-04 | 系统应将每条评分提交存储在其评分方案所关联的评分对象下，并标明提交成员。 | 必须 | 已存储提交可以从正确评分对象访问，并显示作者和时间。 |
| FR-RAT-05 | 系统应允许已认证成员复用其他成员发布的评分方案，创建独立的评分提交。 | 必须 | 两名成员可以针对同一组不可变评分维度提交不同分数。 |
| FR-RAT-06 | **暂定：** 系统应允许成员更新自己的评分提交，并重新计算结果分数。 | 应该 | 获得授权的更新可以修改分数并得到后端重新计算的结果；其他普通成员不能执行该更新。 |
| FR-RAT-07 | 系统应以不会暗示结果客观真实或具有权威性的方式显示个人结果分数。 | 必须 | 评分页面把分数标记为社区观点或娱乐结果。 |

### 5.5 文字感想与评论

| ID | 需求 | 优先级 | 验收证据 |
|---|---|---:|---|
| FR-COM-01 | 系统应允许评分提交的作者在提交中附带一段可选的文字感想。 | 必须 | 文字感想可以与评分提交一起保存，并显示在正确的评分对象下。 |
| FR-COM-02 | 系统应允许已认证成员在另一条有效评分提交下发表评论。 | 必须 | 有效评论显示在所选评分提交下，并标明作者。 |
| FR-COM-03 | 系统应拒绝空评论。 | 必须 | 只包含空白字符的内容不会被保存，并产生明确的验证提示。 |
| FR-COM-04 | **暂定：** 系统应允许成员编辑或删除自己的评论，但不能编辑或删除其他普通成员的评论。 | 应该 | 用户界面和直接 HTTP 请求都会在后端执行所有权检查。 |
| FR-COM-05 | **暂定：** MVP 应采用单层评论列表，不支持嵌套回复。 | 应该 | 评论直接显示在评分提交下，不建立子评论关系。 |

### 5.6 图片

| ID | 需求 | 优先级 | 验收证据 |
|---|---|---:|---|
| FR-MED-01 | 系统应允许已认证成员在自己的评分提交中附加图片。 | 必须 | 有效图片被存储、标明上传者，并显示在正确的评分对象和评分提交下。 |
| FR-MED-02 | 系统应在存储前根据允许的媒体类型和已配置的大小限制验证每个上传文件。 | 必须 | 不允许的文件或过大文件会被拒绝，并且不会作为公开内容提供。 |
| FR-MED-03 | 系统应阻止普通成员修改或删除其他成员的图片。 | 必须 | 后端授权检查拒绝未经授权的图片修改操作。 |
| FR-MED-04 | 管理员移除媒体资源后，系统应停止显示该资源。 | 必须 | 被移除的图片无法通过普通公开页面和媒体 URL 访问。 |
| FR-MED-05 | **暂定：** 系统应在图片被移除后显示中性占位内容，同时保留周围的合法内容。 | 应该 | 被移除图片不会破坏评分提交的布局，也不会删除无关文字和分数。 |

### 5.7 举报与内容管理

| ID | 需求 | 优先级 | 验收证据 |
|---|---|---:|---|
| FR-MOD-01 | **暂定：** 系统应允许已认证成员举报评分对象、评分提交、评论或媒体资源，交由管理员检查。 | 必须 | 举报记录包含举报人、目标、原因、状态和创建时间。 |
| FR-MOD-02 | 系统应为特权管理员提供自定义内容管理面板，并且不得把 Django 内置 admin 作为面向用户的管理解决方案。 | 必须 | 获得授权的管理员可以访问专门构建的面板；普通成员不能访问。 |
| FR-MOD-03 | 系统应允许管理员查找并移除违法、暴力、色情或其他被禁止的社区内容。 | 必须 | 从自定义面板执行移除后，公众无法再访问所选内容。 |
| FR-MOD-04 | 系统应将管理员权限限制在社区内容管理范围内，不得暴露开发者级系统配置。 | 必须 | 自定义面板只包含已经定义的内容管理操作和数据。 |
| FR-MOD-05 | **暂定：** 系统应记录每次内容移除的管理员、目标、原因和时间。 | 应该 | 获得授权的管理员可以查看内容管理审计记录。 |
| FR-MOD-06 | 当管理员移除特定违规图片或评论时，系统应保留无关的合法内容。 | 必须 | 删除子内容不会级联删除整个评分对象或其他无关评分提交。 |

### 5.8 所有权与内容生命周期

| ID | 需求 | 优先级 | 验收证据 |
|---|---|---:|---|
| FR-OWN-01 | 系统应在后端对所有创建、更新和删除操作执行内容所有权及管理权限检查。 | 必须 | 直接构造请求也不能绕过用户界面所呈现的权限限制。 |
| FR-OWN-02 | **暂定：** 在评分对象或评分方案尚无其他社区提交依赖时，系统可以允许创建者编辑其描述文字。 | 可以 | 只有当修改不会重新解释其他成员的关联内容时，编辑才会成功。 |
| FR-OWN-03 | **暂定：** 在另一名成员已经使用评分方案后，系统应阻止对已发布评分维度的破坏性修改。 | 应该 | 已使用的评分维度保持不可变或被版本化，从而保留历史结果分数。 |
| FR-OWN-04 | **暂定：** 系统应使用可见的“内容已移除”状态，而不是把已删除的社区内容悄悄归到另一名作者名下。 | 应该 | 内容归属保持真实，已删除内容不会被显示为另一名成员所创作。 |

### 5.9 AJAX 与交互反馈

| ID | 需求 | 优先级 | 验收证据 |
|---|---|---:|---|
| FR-AJX-01 | 系统应对适合的动态交互广泛使用 AJAX，包括评分输入、评论提交、状态变更和内容管理操作，且不要求刷新整个页面。 | 必须 | 成功操作会在原位置更新相关可见状态。 |
| FR-AJX-02 | 系统应为每个 AJAX 操作显示明确的成功、验证和失败反馈。 | 必须 | 网络错误、验证错误、权限错误和服务器错误不会静默失败或破坏当前页面状态。 |
| FR-AJX-03 | 后端应对 AJAX 请求执行与对应非 AJAX 请求相同的验证和授权。 | 必须 | 直接构造的请求无法绕过业务规则。 |

### 5.10 RESTful API

| ID | 需求 | 优先级 | 验收证据 |
|---|---|---:|---|
| FR-API-01 | 系统应提供至少四个已记录的 RESTful JSON 端点，使外部客户端可以与指定社区资源交互。 | 必须 | API 文档列出端点、HTTP 方法、认证、示例、错误和限制。 |
| FR-API-02 | REST API 应使用适当的 HTTP 方法，在已记录的资源集合中支持创建、读取、更新和删除操作。 | 必须 | 自动化 API 测试验证所支持的 CRUD 矩阵。 |
| FR-API-03 | REST API 应验证输入、返回一致的 JSON 错误响应，并在需要时执行身份认证和所有权检查。 | 必须 | 无效和未授权请求得到适当的非 2xx 状态码，并且不会修改数据。 |

建议的资源端点包括：

- `/api/things/` 和 `/api/things/{id}/`；
- `/api/things/{id}/schemes/` 和 `/api/schemes/{id}/`；
- `/api/schemes/{id}/submissions/` 和 `/api/submissions/{id}/`；
- `/api/submissions/{id}/comments/` 和 `/api/comments/{id}/`；
- `/api/reports/` 和 `/api/reports/{id}/`。

最终 CRUD 矩阵仍为待定。

## 6. 数据需求

### 6.1 初步实体目录

以下模型包含超过课程要求的六张有意义业务表。Django 自动生成的身份认证和会话表不计入数量。

| 实体 | 用途 | 初步字段 |
|---|---|---|
| UserProfile | 通过与认证用户的一对一关系存储社区特有的成员信息 | id, user_id, display_name, bio, avatar_path, created_at, updated_at |
| Thing | 表示一个实体或抽象评分对象 | id, created_by_id, name, normalised_name, subject_type, description, status, created_at, updated_at |
| RatingScheme | 定义一种可复用的评分对象判断方式 | id, thing_id, creator_id, title, description, scale_min, scale_max, formula_version, status, created_at, updated_at |
| Criterion | 定义一个评分维度及其在评分方案中的顺序 | id, rating_scheme_id, name, description, weight, display_order, status |
| RatingSubmission | 存储一名成员对一个评分方案的完整使用结果 | id, rating_scheme_id, author_id, result_score, reaction_text, status, created_at, updated_at |
| CriterionScore | 存储一条评分提交中的一个维度分数 | id, rating_submission_id, criterion_id, score |
| Comment | 存储评分提交下的讨论 | id, rating_submission_id, author_id, body, status, created_at, updated_at |
| MediaAsset | 存储图片元数据和审核状态 | id, rating_submission_id, uploader_id, storage_path, mime_type, byte_size, status, created_at |
| ContentReport | 跟踪请求管理员检查内容的记录 | id, reporter_id, target_type, target_id, reason, details, status, resolved_by_id, created_at, resolved_at |
| ModerationAction | **暂定：** 记录一项内容管理审计事件 | id, moderator_id, target_type, target_id, action, reason, created_at |

### 6.2 必需的关系覆盖

- **一对一：** 认证用户与 UserProfile。
- **一对多：** Thing 与 RatingScheme；RatingScheme 与 Criterion；RatingScheme 与 RatingSubmission；RatingSubmission 与 Comment；RatingSubmission 与 MediaAsset。
- **多对多：** 成员与评分对象通过 RatingSubmission 形成多对多关系。多名成员可以评价多个评分对象，关联业务记录会保留所选评分方案和提交的分数。

### 6.3 数据完整性规则

- 评分对象名称去除首尾空白后不能为空。
- 评分方案必须引用一个有效评分对象。
- 除非后续决策明确允许重复，否则评分维度名称在其评分方案内必须非空且唯一。
- 对于 `(rating_submission, criterion)` 组合，维度分数必须唯一。
- 维度分数必须处于评分方案配置的范围内。
- 一条评分提交不能包含属于其他评分方案的评分维度。
- 派生结果分数必须由后端计算，不得直接接受客户端提交的结果。
- 内容管理和软删除状态必须被明确表示，以避免公开查询意外返回违规内容。
- 如果内容管理审计需要，即使公开图片被移除，也应保留其元数据。

### 6.4 数据保留与删除

准确的数据保留政策仍为待定。建议对内容管理证据所需的社区记录采用软删除，并从公开存储中永久移除违规图片文件。账号删除、匿名化方式和数据保留期限需要后续决定。

## 7. 初步用户旅程

### UJ-01：发现社区观点

1. 用户在搜索框中输入评分对象名称。
2. 系统返回匹配评分对象或无结果状态。
3. 用户打开一个评分对象。
4. 系统显示该对象的评分方案、个人评分提交、结果分数、文字感想、图片和评论。

### UJ-02：创建并评价新对象

1. 已认证成员搜索一个评分对象。
2. 如果没有合适的匹配项，成员创建该对象。
3. 成员创建评分方案并定义评分维度。
4. 成员为每个评分维度打分。
5. 成员可以添加文字感想和图片。
6. 系统验证输入、计算结果分数，并将评分提交发布在评分对象下。

### UJ-03：复用其他成员的评分方案

1. 已认证成员打开一个评分对象。
2. 成员选择一个已有评分方案。
3. 系统显示该方案不可变的评分维度。
4. 成员为所有评分维度提交分数。
5. 系统计算并发布一条归属于该成员的独立结果分数。

### UJ-04：讨论一条评分

1. 已认证成员打开一条评分提交。
2. 成员提交一条非空评论。
3. 系统进行验证，并在不刷新整个页面的情况下显示该评论。

### UJ-05：管理违规内容

1. 管理员打开自定义内容管理面板。
2. 管理员直接查找内容，或通过内容举报找到内容。
3. 管理员检查该贡献及其上下文。
4. 管理员移除违规目标并记录原因。
5. 公开页面停止提供被移除的目标，但保留无关的合法内容。

## 9. 非功能需求

### 9.1 易用性与无障碍

- NFR-USE-01：系统应在约定的桌面端和移动端视口范围内提供一致、现代且响应式的界面。
- NFR-USE-02：系统应提供清楚的标签、键盘可操作控件、有意义的焦点状态，以及信息图片的文字替代内容。
- NFR-USE-03：系统应明确区分加载、空内容、成功、验证错误、权限错误和服务器错误状态。
- NFR-USE-04：在不降低可读性、无障碍性或实现可行性的前提下，系统应保留现有原型轻松有趣的视觉风格。

### 9.2 性能与可靠性

- NFR-PERF-01：生产系统应支持至少五名并发用户，且不出现可识别的应用错误。
- NFR-PERF-02：当外部 API 响应缓慢或不可用时，系统应优雅降级；创建、评分、浏览和内容管理等核心功能必须继续运行。
- NFR-PERF-03：可复用的外部数据应被缓存或存储在本地，以避免不必要的重复 API 调用。
- NFR-REL-01：EC2 服务器重启后，生产服务应自动恢复，无需人工启动进程。
- NFR-REL-02：应用错误不得向用户暴露堆栈跟踪或内部实现细节。

### 9.3 安全与隐私

- NFR-SEC-01：身份认证、授权、验证、分数计算和内容管理检查都应由后端强制执行。
- NFR-SEC-02：系统应使用 Django 防护机制和安全实现实践抵御 XSS、SQL 注入和 CSRF。
- NFR-SEC-03：生产系统应使用 HTTPS，并设置 `DEBUG=False`。
- NFR-SEC-04：系统不得通过 HTTP 暴露源代码、密钥、环境文件、私钥、命令历史中的秘密或服务器敏感文件。
- NFR-SEC-05：生产数据库访问应使用适合应用运行操作的最小权限。
- NFR-SEC-06：SSH 访问应使用私钥认证，并禁用基于密码的登录。
- NFR-SEC-07：系统应把上传图片视为不可信数据，在存储前进行验证，并以不可执行的方式提供图片文件。
- NFR-SEC-08：最终安全设计应实施课程认可的两项基础安全措施和一项高级安全措施；具体措施仍为待定。

### 9.4 可维护性与测试

- NFR-MNT-01：Django 后端应遵循 MVT，并清楚分离模型、视图、模板、服务、验证和权限职责。
- NFR-MNT-02：URL 路由、静态文件、媒体文件、配置和错误处理应保持模块化并具有文档说明。
- NFR-TST-01：后端测试应覆盖模型、视图、API 端点、权限、分数计算、验证、所有权、内容管理和失败情况。
- NFR-TST-02：项目应以关键后端文件约 85% 的有效覆盖率为目标，并记录团队同意排除的文件。

## 10. 技术与课程约束

- 后端必须使用 Django。
- 数据库必须包含至少六张有意义的业务表，并展示一对一、一对多和多对多关系。
- 系统必须提供至少四个 RESTful JSON 端点，并在已记录的资源集合中支持 CRUD。
- 系统必须提供面向非开发者的自定义内容管理面板，不得把 Django 内置 admin 作为提交的管理界面。
- 前端必须包含自定义 CSS 和具有实际意义的自定义 JavaScript，并在适合即时反馈的地方广泛使用 AJAX。
- 系统必须通过 Django 后端集成至少一个能够增加实际价值的外部 API，并提供缓存和失败降级；具体 API 待定。
- 团队必须为 Assignment 2 选择 Modern Frontend Design 或有实际意义的 WebSocket 集成；具体选择待定。
- 至少五项核心能力必须要求身份认证。
- 项目必须使用 Django 内置测试框架并编写有意义的后端测试。

- Nginx 必须作为反向代理，并提供静态文件和媒体文件。
- Django 应用必须由 uWSGI 运行。
- 必须按照作业要求配置 22、80 和 443 端口；HTTP 预计重定向到 HTTPS，但仍需导师确认。
- 部署后的系统必须通过 Assignment 3 的全部十二项安全检查。

## 11. 初步架构方向

当前课程仓库包含一个 Django 5.2.17 起始项目。另一个公开原型使用 React 和 Vite 实现本地 Score-O-Matic 工具。

推荐的低风险实现方式为：

- 使用 Django 实现模型、身份认证、权限、视图、REST API、分数计算、内容管理和媒体处理；
- 主要页面使用 Django templates；
- 根据原型的视觉语言编写自定义 CSS；
- 使用针对性的 JavaScript 和基于 Fetch 的 AJAX 实现评分、评论、搜索反馈和内容管理；
- 本地开发使用 SQLite，生产数据库选择延后决定；
- 核心分数计算流程不依赖大模型。

该方向标记为 **暂定**。保留 React 前端仍然可行，但会增加两人初学团队的集成和部署工作量。

## 13. 风险

| 风险 | 影响 | 初步应对方式 |
|---|---|---|
| 用户任意创建评分对象会导致重复或身份含糊 | 搜索结果和社区内容被分散 | 规范化名称、显示相似匹配，并在实现前定义合并规则 |
| 不同评分方案产生无法直接比较的结果分数 | 评分对象层级的聚合分数可能误导用户 | 在聚合规则确定前，只显示按评分方案区分的个人提交 |
| 用户上传违法、暴力或色情图片 | 带来安全、评分和法律风险 | 严格上传验证、用户举报、自定义内容管理、删除和审计记录 |
| 两名初学者需要学习完整技术栈 | 进度和质量风险 | 保持较小 MVP、优先 Django templates、持续测试，并推迟 AI/WebSocket |
| 外部 API 或大模型不可用 | 核心流程可能中断 | 所有核心评分功能保持本地运行，外部缓存数据只用于增强体验 |
| 其他成员复用后，已发布评分维度又被修改 | 历史分数无法复现 | 使用过的评分方案保持不可变或进行版本化 |
| Assignment 3 采用阶梯式检查 | 缺少一个部署或安全项就可能损失大量分数 | 从项目开始就把每项 A3 检查视为必须需求 |

## 14. 待确认问题

在本 SRS 成为正式提交基线前，必须解决以下问题：

1. 评分对象页面只显示每条个人结果分数，还是还要显示一个社区总分？
2. 如果显示社区总分，使用不同评分方案的提交应如何聚合，才能避免误导？
3. 评分输入采用 1-5 星、0-10、0-100、字母等级还是其他范围？
4. 评分维度是否像现有原型一样具有数字权重，还是 MVP 中全部等权？
5. 结果分数的准确计算公式和舍入规则是什么？
6. “任何人都可以添加内容”是指任何已认证成员，还是允许匿名写入？
7. 同一成员能否针对同一评分方案提交多条评分？
8. 评分方案发布前后或被其他成员使用后，创建者能否继续编辑？
9. 评分提交中的文字感想是否与后续评论属于两个不同概念？
10. 评论只支持单层列表，还是允许嵌套回复？
11. 一条评分提交可以包含一张还是多张图片？文件大小、类型和尺寸限制分别是什么？
12. 图片应附属于评分对象本身、评分方案，还是单条评分提交？
13. 违法、暴力、色情或其他违规内容的准确内容政策是什么？
14. 成员是否可以举报内容，还是必须由管理员自行发现全部违规内容？
15. 作者能否编辑或删除自己的评分对象、评分方案、评分提交、图片和评论？
16. 如何发现、区分、合并或重定向重复评分对象？
17. MVP 只使用自由输入的对象名称，还是也包含分类和搜索标签？
18. 创建评分对象时，除名称和实体/抽象类型外，还需要哪些信息？
19. 哪些页面公开访问，哪些页面需要身份认证？
20. 团队将实施哪两项基础安全措施和哪一项高级安全措施？
21. 哪个外部 API 能够增加价值，同时不成为核心依赖？
22. 实现采用 Django templates，还是保留 React 前端？
23. 生产环境使用哪种数据库？
24. 支持哪些浏览器、视口大小和无障碍目标？

本草稿记录了已确认的产品概念和为满足课程要求而提出的 MVP 建议。它尚未被批准为团队共同的正式需求基线。团队应按照决策树顺序解决所有待确认问题，更新需求和验收标准，然后明确批准新版本，之后才能把实现内容视为已经承诺的项目范围。
